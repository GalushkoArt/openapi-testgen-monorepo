# Repository Guidelines

Canonical guidance for AI agents and automation working in this repository. `CLAUDE.md` imports
this file; keep tool-neutral guidance here and tool-specific additions there.

## Project Overview

OpenAPI Test Generator is a Kotlin monorepo that generates test cases from OpenAPI/Swagger
specifications: negative (4xx) cases by default, plus an optional baseline positive (2xx) case per
operation (`includeValidCase`). It ships as a Gradle plugin, an npm/native CLI, and a programmatic
API (`TestGenerationRunner`).

## Project Structure & Module Organization

Gradle composite build (`settings.gradle.kts` uses `includeBuild` per module):

- `build-logic/`: convention plugins for centralized build configuration
- `model/`: shared data models (`TestCase`, `TestSuite`, `Outcome`, `GenerationReport`)
- `example-value/`: schema-derived example value generation; owns the `SchemaValueProvider` SPI
- `core/`: test generation engine (providers, rules, generators, budgets)
- `pattern-value/`: regex-based value generation (no `core` dependency)
- `pattern-support/`: pattern integration with `core` (module + rule + settings extractor)
- `generator-template/`: Mustache `template` generator (RestAssured template sets)
- `distribution-bundle/`: shared default wiring for CLI and Gradle plugin (`TestGenerationRunner`)
- `plugin/`: Gradle plugin; `cli/`: command-line interface (optionally native via GraalVM)
- `samples/`: runnable usage projects consuming the published plugin

Standard layout across modules: sources in `*/src/main/kotlin`, tests in `*/src/test/kotlin`,
fixtures in `*/src/test/resources`, templates in `generator-template/src/main/resources`.

Dependency direction flows inward: `plugin`/`cli` → `distribution-bundle` → feature modules →
`core` → `example-value` → `model`. Never reverse it.

## Architecture Essentials

- **Provider-rule model**: `TestCaseProvider` implementations orchestrate generation per aspect
  (parameters, request body, auth); `SchemaValidationRule` / `AuthValidationRule` encode
  individual OpenAPI constraints.
- **Manual wiring, no reflection for discovery**: rules/generators are wired explicitly
  (`BuiltInRules`, `BuiltInGenerators`, `TestGenerationModule`); this keeps GraalVM native images
  working. Mustache templates and the OpenAPI parser still use reflection (config under
  `cli/src/main/resources/META-INF/native-image/`).
- **Determinism**: rules, generators, and modules are sorted (class name / id); same spec + settings
  always produce the same output. Sort any new collection you introduce.
- Deep dive: `docs/concepts/architecture.md`.

## Build, Test, and Development Commands

- `./gradlew check`: lint, tests, API compatibility across all included builds plus samples
- `./gradlew :core:test` / `:plugin:test` / `:cli:test`: run module tests
- `./gradlew :core:test --tests "ValidCaseBuilderTest"`: run a single test class/method
- `./gradlew detekt`: Kotlin linting (config: `build-logic/config/detekt.yml`)
- `./gradlew :example-value:apiCheck`: binary-compatibility check for a module's public API
- `./gradlew :cli:installDist` / `:cli:run --args="--help"` / `:cli:nativeCompile`
- Docs: `./gradlew docsBuild` (strict mkdocs; do NOT run bare `mkdocs build` — the changelog page
  is generated by Gradle and strict mode fails without it); `./gradlew docsServe` for local preview.

## Coding Style & Naming Conventions

- Indentation: 4 spaces; max line length: 160 (see `.editorconfig`)
- Kotlin naming: `PascalCase` classes, `camelCase` functions/vars, `UPPER_SNAKE_CASE` constants
- Prefer immutable data (`data class`, immutable collections); avoid `!!`; validate with
  `require(...)` / `check(...)`; never swallow exceptions
- SLF4J parameterized logging (no string concatenation)
- Keep edits minimal and follow `.cursor/rules/01-kotlin-style.mdc` (detekt enforces formatting)

## Testing Guidelines

- Frameworks: JUnit 5, AssertJ, Allure; tests mirror the source structure
- Deterministic, isolated, no network I/O; fixtures live in `*/src/test/resources`
- Use `@DisplayName`; extend `ValidationRuleTest` for rule tests and `TestProviderTest` for
  provider tests where applicable; parameterized tests use `@MethodSource`
- **Precise assertions**: exact string matches (`isEqualTo`, not `contains`), exact collection
  contents (`containsExactlyInAnyOrder`, verify sizes), complete error messages
- Generator outputs are compared against snapshot JSON fixtures; regenerate with
  `UPDATE_SNAPSHOTS=true ./gradlew :core:test :cli:test` when output legitimately changes, and
  review the fixture diff
- Integration tests parse specs with `ParseOptions().apply { isResolveFully = true }` and compare
  suites via `usingRecursiveComparison()`

## Acceptance Criteria (any change)

- `./gradlew :core:check :plugin:check` passes (Java 21, Kotlin 2.x) — run the `check` of every
  module you touched
- No detekt violations in changed files
- Configuration-cache compatibility preserved (no heavy work at configuration time, no
  `Task.project` at execution time)
- Public API changes are deliberate and covered by `apiCheck` (`.api` dumps updated via
  `apiDump` when intended)
- Deterministic output ordering (sort by class name or key)
- User-visible changes get a `CHANGELOG.md` entry under `Unreleased`

## Documentation Guidelines

- The docs site (`docs/`, built by MkDocs Material) is canonical; module READMEs are thin
  GitHub-facing landing pages that link to it — do not re-add option tables to READMEs
- Every claim in docs must be verified against source code first; each fact lives in exactly one
  page, cross-link otherwise (see `.claude/skills/project-docs/SKILL.md` for the full authoring
  guide)
- Site pages need `description:` frontmatter; new pages go into `mkdocs.yml` nav, then regenerate
  the map: `python3 skills/project-docs/scripts/sync_docs_map.py` (needs PyYAML; the
  `.gradle/docs-python` venv has it)
- `context7.json` configures the context7.com index (agent-facing `rules`, folder exclusions);
  keep its `rules` in sync with behavior changes

## Engineering Principles

SOLID, DRY, KISS, YAGNI. Keep parsing (OpenAPI), generation (providers/rules), and output
(generators) separate. Fail fast with precise, actionable errors. Don't add speculative features
or options.

## Commit & Pull Request Guidelines

- Commit messages are short, imperative summaries (no conventional-commit prefix required)
- PRs should include a concise description, modules touched, and tests run (e.g., `./gradlew
  :core:check :plugin:check`)
- If you change generators/templates, include updated fixtures or updated example output under
  `samples/`
